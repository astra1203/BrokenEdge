## 3. M1：库存与存档一致性（P1 主线）

### WP-05 TD-005 库存事务接口（L 的第一步）

在 `UExtractionInventoryComponent` 上新增权威修改入口，**先只加接口和测试，不迁移调用方**：

```cpp
// ExtractionInventoryComponent.h
enum class EExtractionInventoryCommit : uint8 { Ok, NoChange, Stale, Rejected, WeaponSyncFailed };

struct FExtractionInventoryResult
{
	EExtractionInventoryCommit Code = EExtractionInventoryCommit::Rejected;
	FString Error;
	bool Ok() const { return Code == EExtractionInventoryCommit::Ok || Code == EExtractionInventoryCommit::NoChange; }
};

// 单容器：在候选副本上执行 Edit；成功则保证 Revision 至少推进一次、SyncWeapons、Changed。
// ExpectedRevision != INDEX_NONE 时先做过期检查。SyncWeapons 失败则还原并再次 SyncWeapons。
FExtractionInventoryResult Mutate(TFunctionRef<bool(FExtractionContainer&, FString&)> Edit,
                                  int32 ExpectedRevision = INDEX_NONE, bool bSyncWeapons = true);

// 双容器（背包 + 战利品/掉落物）：两边候选副本一起修改、一起提交或一起回滚。
static FExtractionInventoryResult MutatePair(UExtractionInventoryComponent& Inventory, AExtractionLootActor& Loot,
	TFunctionRef<bool(FExtractionContainer& Inv, FExtractionContainer& Other, FString&)> Edit,
	int32 ExpectedInventoryRevision = INDEX_NONE, int32 ExpectedLootRevision = INDEX_NONE);
```

规则（写进头文件注释）：
1. 仅服务器调用（`check(GetOwner()->HasAuthority())`）。
2. Edit 返回 false → 原状态完全不变，返回 `Rejected`。
3. Revision 规则：Edit 后若候选 Revision 未变化且内容有变化，补 `++Revision`；ExtractionItems 原语内部的推进保留。
4. 提交顺序：赋值 → `SyncWeapons()` → 失败则还原两个容器并再次 `SyncWeapons()` → 成功后 `Changed()`（对 Loot 调 `Loot.Changed()`）。这与 `ExtractionInteractionComponent.cpp:427-451` 现有手写顺序一致，是把它收拢而不是改语义。
5. 来源批次（Origin）和 GUID 守恒由 Edit 内的原语负责，事务层在 `WITH_DEV_AUTOMATION_TESTS` 下做一次“GUID 集合 + 各定义数量和”的前后对比断言（仅调试校验，不改行为）。

**测试**（扩展 `ExtractionInventoryTests.cpp`，新前缀 `BrokenEdge.Extraction.Inventory.Transaction.*`）：Edit 拒绝不改状态；过期 Revision 返回 `Stale`；用测试钩子让 `SyncWeapons` 失败（仿照持久化的 `FailNextWrite`）→ 两容器均还原、Revision 不变；成功时 Revision 恰好推进一次。

### WP-09 日志滚动（L）

前提：每条记录本身就是完整状态，所以以“最新完整状态”开启新段不丢信息。

- **格式**：记录头 `Header[1]` 版本从 1 升到 2，新增字段 `Flags`（bit0 = SegmentStart，表示本条可作为重放起点）。读取兼容 v1（视为非段首）。
- **滚动流程**（触发条件：日志字节数或记录数超过 WP-08 定出的阈值，在一次成功 `Commit` 之后执行）：
  1. 把当前 `State`（已刷盘的那份）以 SegmentStart 记录写入 `Store.journal.next`，`Flush(true)`，重新读回校验 CRC 与 `Validate`。
  2. `Store.journal` → `Store.journal.gen<Sequence>`（保留最近 N 代，N 默认 3，可配置）。
  3. `Store.journal.next` → `Store.journal`。
  4. 任何一步失败：保留原 `Store.journal`，删除 `.next`，记录 Warning，**不进入 Faulted**（滚动失败不影响正确性，只影响容量）。
- **Load 改动**：允许首条记录为 SegmentStart 且 `Sequence > 1`；之后仍要求严格连续。启动时若发现 `.next` 残留：主日志存在则删 `.next`；主日志缺失而 `.next` 有效则提升 `.next`（处理第 2、3 步之间崩溃）。
- **与旧版迁移的关系**：`PreserveLegacyJournal`（v<7 备份）逻辑不动，滚动只在 `State.Version` 为当前版本时启用。
- **测试**（扩展 `ExtractionPersistenceTests.cpp`）：每一步之后注入失败/模拟崩溃（截断、缺文件、`.next` 残留），重启后 `State` 与滚动前逐字段相等、Sequence 连续、无重复回执；v1 旧日志可读；连续滚动 N+2 次后旧代数受控。

### WP-10 记录保留策略（L，需先定规则）

单条记录变大的根源是 `Profiles[].EconomyReceipts` 与 `Raids` 只增不减。需要先**确认以下规则**再写代码（列为本 WP 的设计评审项）：

| 数据 | 建议规则 | 必须保持的不变量 |
| --- | --- | --- |
| `Raids` 中已关闭（已结算/已恢复）记录 | 关闭超过 K 局或 T 天后移出 `State`，摘要（ID、结果、时间）进入滚动时的归档代文件 | 未关闭局永不回收；回收后同一 Raid ID 的结算请求必须被拒绝而不是重新发放——需要保留一个“已关闭 Raid ID”的紧凑集合或以 Sequence/时间下界判定 |
| `EconomyReceipts` | 保留每个档案最近 M 条，或保留期 = 客户端重试有效期的若干倍 | 重试窗口内的重复请求仍能命中幂等回执；窗口外的旧请求ID被拒绝（请求需带时间或序号下界） |
| `Exported` 来源批次 | 随所属 Raid 关闭后一并回收 | 背包/仓库中仍引用的来源批次不能回收（回收前做引用扫描） |

- 实现位置：在 `Commit` 构造候选状态的路径上执行修剪，修剪本身也是一次普通 `Commit`（走完整验证与 CRC），不旁路写文件。
- `State.Version` +1，迁移函数对旧档案做一次修剪并保留 `.v<旧版本>.bak`（复用现有备份机制）。
- **验收**：WP-08 大档位数据下单条大小稳定在阈值内；超窗口重放回执被拒、窗口内重放命中；未结束对局在修剪后仍能正常结算或恢复；无重复发放、无丢账。

> 异步写盘或换数据库不在本方案范围，待 WP-08 数据表明同步 Flush 成为瓶颈时另议。
