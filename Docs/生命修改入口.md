# 生命修改入口

WP-12：`ABrokenEdgeCharacter::ApplyVitalsChange` 是角色运行时 Health/Shield 的唯一服务器写入口。构造默认值与客户端属性复制不属于玩法写入；`Prototype/MyCharacter` 原型有独立状态，不接入正式角色。

| 调用者 | 计算阶段 | 应用阶段 |
| --- | --- | --- |
| `ReceiveDamage` | `CalculateIncomingDamage` 调用一次 GameMode `CalculateDamage` | `ApplyResolvedDamage` → `ApplyVitalsChange(Damage)` |
| `ExtractionHealth::Bullet` | 友伤/阶段过滤一次；弹药倍率；库存事务扣护甲耐久 | 同上；实际掉血决定创伤 |
| `ExtractionHealth::Explosion` | 友伤/阶段过滤一次 | 同上；实际掉血决定出血 |
| `ExtractionHealth::Treat` | 权威、存活、未倒地、治疗需求 | `ApplyVitalsChange(Healing)`；返回实际应用结果，不对拒绝治疗消耗物品 |
| `ExtractionHealth::TickStim` | 服务器计时、存活资格、持续与快速恢复量 | 同上 |
| `ExtractionHealth::TickComponent` 出血 | 可行动、出血间隔 | `ApplyVitalsChange(Bleeding)`；绕过护甲，不重复计算武器伤害 |
| `BuffComponent::HealRampUp/ShieldRampUp` | 有限正数增量/时长/帧间隔，剩余恢复预算限制 | `ApplyVitalsChange(Healing)`，删除手动 HUD 更新 |
| `ExtractionAbilities::Complete` 救援 | 服务器目标/距离/动作检查，恢复 Alive | 合并 HP/Shield 为一次 `Restore` |
| `ExtractionGuard` 两处初始化 | 服务器守卫初始化 | 合并 HP/Shield 为一次 `Restore` |
| `ExtractionDriverTests` 场景准备 | 测试夹具设置 | `Restore` |

旧的 `SetHealth/SetShield` 已删除。入口拒绝非服务器、非有限值、已死亡及倒地治疗；数值钳制到上限。旧模式伤害先扣 Shield；Extraction 的护甲由库存中的装备耐久处理，不使用旧 Shield 吸收。

倒地池与生命阶段仍由 GameMode/PlayerState 管理：伤害入口转交 `DamageDowned` 或 `DefeatCombatant`，返回本次实际 HP、Shield、DownHealth 增量及倒地/死亡状态。救援先恢复 PlayerState，再一次恢复角色 HP/Shield；返回的 DownHealth 增量不包括这次外部复位。

服务器每次非空变化广播一次 `OnVitalsChanged`，HUD 订阅该事件；无变化、无效请求不广播。客户端继续通过既有 Health/Shield RepNotify 更新 HUD；事件不是可靠的逐命中网络事件，复制可以合并中间状态。观察者的 Extraction HUD 继续读取复制状态。

`CalculateDamage` 应保持幂等，但每次入射伤害只调用一次。测试构建通过 `TestDamageCalculations` 计数验证。此前重复调用的是模式/友伤过滤，并没有证据表明现有伤害数值被乘算两次。

验证入口：`run_editor_task.py vitals`（临时 World）、`vitals-pie`（真实训练场 PIE）和 `vitals-net-pie`（同进程专服 + 两个真实网络客户端）；传入统一 `--engine` 与唯一 `--tag`。PIE 覆盖爆炸、友伤、护甲破损、医疗与 Buff、倒地池、实际救援请求/完成、出血致死。网络用例使用 150 ms 延迟、5% 丢包，检查拥有者及观察者的 HP/Shield/倒地池、止血、护甲所有者复制和救援请求。独立进程/打包双端及 HUD 视觉仍须另外验收。

## 2026-11-14 恢复预算与救援请求修正

帧时间跨过恢复结束点时，旧 Buff 实现仍应用完整 `Rate * DeltaTime`，导致额外回血/回盾；例如 10 HP/1 s 用两帧 0.75 s 推进会恢复 15 HP。现在每帧最多消耗剩余预算。零、负值、NaN、Infinity、速率溢出/下溢的请求在修改状态前拒绝，保留正在执行的合法恢复；非法帧间隔也不消耗预算。

真实网络救援暴露了另一处缺陷：服务器 `OnPossess` 的取消路径通过 `ReleaseRescue` 消耗本地序号，把 `LastSequence` 推进到 2；远端客户端的第一次请求（序号 1）因此被丢弃。服务器取消现在直接执行 `Cancel()`；客户端取消继续携带递增序号走可靠 RPC，旧请求过滤仍然有效。网络测试先验证首次救援，再取消、重放旧请求、重新请求，等待正常 5 秒计时完成。
