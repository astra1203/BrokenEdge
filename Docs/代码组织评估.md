# BrokenEdge 代码组织评估

日期：2026-11-09

## 结论

头文件和 cpp 放在一起对这个项目没问题，不用改。真正值得整理的是 `Extraction/` 目录的结构，以及 `test/` 和 `Tests/` 两个目录名容易混淆。

## 为什么不用拆 Public/Private

- `Public/` 和 `Private/` 不是代码风格，它的作用是控制"哪些头文件给别的模块用"。UBT 会把 `Public/` 加进依赖模块的 include 路径，`Private/` 对外不可见。这对引擎模块和要分发的插件有意义。
- 游戏主模块（`BrokenEdge`）基本只有自己用。UE 官方的 C++ 模板生成的就是平铺结构，Lyra 的 `LyraGame` 模块也是按功能分文件夹，`.h` 和 `.cpp` 放在一起。
- `StingerTools` 依赖 `BrokenEdge`，用的是 `#include "BrokenEdge/Extraction/ExtractionGameMode.h"` 这种带模块名的完整路径，能正常编译，所以不拆也不影响跨模块引用。
- `StingerTools` 本身用的是 Public/Private，`BrokenEdge` 是平铺。两种写法共存问题不大。如果以后要把某块功能抽成插件或共享模块，再给那个模块拆就行。

## 真正值得整理的地方

### 1. `Extraction/` 太大，而且和顶层目录重复（最值得改）

- 这一个文件夹里平铺了 86 个文件，混着 GameMode、PlayerController、各种 Widget、Component、场景物件（Door、Zipline、Water、Drawbridge）、投掷物、AI（Guard、PatrolArea），还有 `WeaponRangeGameMode`。
- 顶层又已经有 `GameMode/`、`PlayerController/`、`UI/`、`Weapon/`、`Component/`，等于"按类型分"和"按功能分"两套规则混在一起。比如找一个 PlayerController，现在得猜它在哪边。
- 建议定一个主规则。项目现在的重心是 Extraction 玩法，所以推荐按功能分，在 `Extraction/` 下再分子目录：

| 子目录 | 放什么 |
| --- | --- |
| `Core/` | GameMode、State、PlayerController |
| `Inventory/` | 背包、物品、战利品 |
| `Combat/` | 战斗、近战、生命值 |
| `Throwables/` | 破片手雷、烟雾弹、兴奋剂飞镖 |
| `AI/` | Guard、PatrolArea、Navigation |
| `World/` | 门、桥、吊桥、滑索、水、玻璃 |
| `UI/` | 各种 Widget、UI 样式 |
| `Persistence/` | 存档、账号、成长 |
| `Map/` | 地图定义、注册表、区域流送、战术地图 |

### 2. `test/` 和 `Tests/` 同时存在

- `Tests/` 是自动化测试，每个文件都有 `WITH_DEV_AUTOMATION_TESTS` 保护，没问题。
- `test/` 里是 `MyCharacter`、`TestActorMove`、`CombatObserver` 这类试验代码，会跟着游戏一起编译。`GameMode/BrokenEdgeGameMode.cpp` 第 10-11 行还 include 了其中两个，说明正式代码依赖了试验目录。
- 建议给 `test/` 改个名（比如 `Sandbox/` 或 `Prototype/`），免得和 `Tests/` 搞混。`CombatObserver` 如果是正式在用的，就挪到对应的功能目录。

### 3. 可选：把测试放进单独的模块

测试代码已经有宏保护，现在这样可以接受。以后测试再变多，可以单独建一个 `BrokenEdgeTests` 模块，这样主模块更干净，增量编译也更快。

## 改动影响

改 `Extraction/` 的目录结构要动很多 include 路径，包括 `StingerTools` 里引用 `BrokenEdge/Extraction/...` 的地方。蓝图引用的 C++ 类路径一般不受影响，因为它们按模块名和类名解析，不看文件路径。
