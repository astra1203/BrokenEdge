# BrokenEdge 搜打撤项目代码规范与现有代码审查

审查日期：2026-10-29。源码基线：`0711fc2ea8c4410eeedeb5429f29e93148eda045`。

目标：支撑类似“三角洲行动航天基地”的搜集、战斗、撤离体验，建设可持续迭代的联机 UE 项目。玩法参照不等于掌握原游戏内部实现，本文不推测其代码架构。

审查覆盖背包、物品事务、交互、战斗同步、结算持久化和背包 UI；不宣称完成了全项目、全部蓝图或资源审计。审查时工作区已有 `LootingMainView.cpp` 注释修改及未跟踪的《背包系统实现原理.md》，均保留。本文没有修改实现、运行编译、PIE、多人进程或性能测试。行号为审查时定位提示，后续优先按函数名查找。

## 1. 当前结论与判断标准

项目已经具有服务器物品事务、拥有者可见库存、搜索脱敏、来源追踪、持久化日志和自动化测试基础。当前优先级应是补齐失败路径、收敛状态修改入口、降低跨组件耦合，然后依据测量优化性能。单纯增加注释或统一缩进，不能解决库存与武器状态一致性问题。

本文采用两套独立标记：

| 标记 | 含义 |
|---|---|
| 源码确认 | 已看到实现事实；不等于运行时已复现故障 |
| 条件性风险 | 仅在资源缺失、生命周期变化、异常输入等条件下可能发生，需测试确认 |
| 待测量 | 已发现成本来源，但尚无耗时、带宽或卡顿证据 |
| P1 | 优先处理的一致性或失败恢复问题 |
| P2 | 持续迭代中的职责、性能、可观测性问题 |
| P3 | 可读性、规范一致性及工具完善 |

本次没有证据足以判定一个已复现、应立即阻断发布的 P0 故障。下文规范是该项目的建议基线，不代表当前代码已全部满足。

## 2. 应遵守的代码规范

### 2.1 C++ 可读性与改动纪律

Epic 的 C++ 规范可作为命名、类型前缀、布尔 `b` 前缀和类组织的基础。标识符应表达职责，避免作用域较大时仍使用过度缩写。项目可明确采用中文说明注释，这是相对 Epic 英文注释要求的团队约定。参见 [Epic C++ Coding Standard](https://dev.epicgames.com/documentation/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine)。

本项目建议执行以下规则：

| 等级 | 规则 | 在本项目中的落点 |
|---|---|---|
| 必须 | 新增类型遵守 `U/A/F/E/I` 等 UE 前缀；布尔使用 `b` 前缀 | 新代码使用 `bFromLoot`，不要继续扩散 `FromLoot` 风格 |
| 必须 | 一个语句表达一个操作；资产修改、分支和循环使用明确大括号 | 不将多级 `for/if` 和写操作压在同一行 |
| 必须 | 业务变量描述含义 | 用 `Inventory`、`Item`、`Request` 替代跨越较多逻辑的 `I`、`R`；短循环下标可保留 |
| 必须 | 接口说明前置条件、权威端、失败语义和副作用 | `SyncWeapons` 的失败是否保留旧装备；`DropAll` 失败是否允许离局 |
| 推荐 | 类型明确时使用 `auto`，业务边界和复杂返回值优先明确类型 | 不依赖读者跳转函数才能判断指针、引用还是容器副本 |
| 推荐 | 头文件描述契约，实现注释描述原因和不变量 | 避免 `.h/.cpp` 逐句复制相同说明，形成双份维护 |
| 必须 | 保持修改范围可评审 | 注释、格式整理、行为修改分开提交；不借规范整治改玩法默认值 |

不要为了满足行数指标机械拆函数。拆分依据应是独立职责、可测试边界和失败处理，而不是每个函数必须少于某个固定行数。现有反射属性改名需检查蓝图、序列化和兼容迁移，不能全局文本替换。

### 2.2 UE 对象、资源与生命周期

- **必须**：需保持存活的 UObject 成员使用适当的反射强引用，例如 `UPROPERTY` 下的 `TObjectPtr`；观察引用使用 `TWeakObjectPtr` 并在使用时验证。裸指针局部借用并非一概错误，但不得跨越对象销毁或数组重分配继续使用。
- **必须**：`FExtractionContainer::Find` 返回的数组元素指针，在增删或替换 `Items` 后重新获取。持久化 `Commit` 替换状态后，同样不能保留旧快照内部指针。
- **必须**：定时器、委托和异步回调明确取消、解绑或失效策略；在切图、退出、Pawn 更换和 PIE 拆卸时仍保持安全。
- **必须**：区分“必定存在的构造期依赖”和“运行时可能暂缺的对象”。前者用清晰不变量和开发诊断，后者返回明确失败；不要到处加静默空判断来掩盖初始化错误。
- **推荐**：资源按定义 ID 管理，生成前验证定义、武器类和所需资产；首次加载放在可控阶段，避免交互热路径意外同步加载。
- **按规模评估**：Asset Manager、软引用和异步加载。引入它们时必须补齐加载失败、取消和 Cook 资产覆盖验证，不以“全改软引用”作为完成标准。

### 2.3 状态归属与组件职责

UE 联机采用服务器权威的客户端—服务器模型。客户端拥有本地输入和表现，不拥有物品数量、伤害或撤离收益的最终裁决权。参见 [Networking Overview](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine)。

建议明确以下边界，而不立即拆成大量模块：

| 层 | 应负责 | 不应独立决定 |
|---|---|---|
| Widget / 本地控制器 | 输入意图、拖拽预览、等待状态、结果显示 | 背包资产最终增减、治疗完成、结算收益 |
| 服务器操作入口 | 权限、会话、版本、动作互斥，组织一次事务 | 仅凭客户端给出的 ID 信任所有权 |
| 物品规则 | 占格、堆叠、装备兼容、数量和来源守恒 | 世界 Actor 生成、UI 文本和网络发送 |
| 库存组件 | 局内物品状态和受控修改入口 | 包揽镜头、动画、配置、持久化实现 |
| 装备同步层 | 由已接受状态构建武器表现并报告失败 | 成为另一套可独立增加资产的库存 |
| 战斗层 | 射击校验、预测回执、装填时序及弹药同步协议 | 绕过来源守恒直接补弹 |
| 持久化层 | 持久提交、幂等结算、恢复和版本迁移 | 未提交成功就告诉上层资产已入库 |

弹匣运行值目前存在于武器 Actor 和物品实例两处。规范应明确每个阶段谁写、何时同步、何时捕获；不能简单宣称“只有一份数据”，也不能要求每次表现变化都先刷盘。

### 2.4 事务、复制与错误处理

**必须维护的不变量：**

1. 一次转移成功后，源与目标及来源批次数量守恒；失败后不发布半完成状态。
2. 重复请求不得重复执行；过期版本不得覆盖新状态；RPC 可靠送达不替代业务幂等。
3. 距离、可见性、搜索权限、目标所有权和动作互斥由服务器重新判断。
4. 未搜索物品的受限数据不应进入该客户端的复制视图；客户端 UI 隐藏不能替代数据隔离。
5. 地面掉落创建失败时不丢弃原资产；失败结果必须能传回控制角色销毁或离局的上层。
6. 结算以持久提交为成功边界；死亡、撤离、退出和断线之间必须有确定的终态与幂等规则。
7. 客户端回执与复制状态可能分时到达，不能收到成功文本就假定所有属性已经更新。

推荐将“成功/错误码/关联请求号/必要上下文”作为操作结果，再由 UI 映射本地化 `FText`。这是后续接口建议，本次不新增类型。服务器的正常拒绝使用稳定错误码；非预期不变量破坏使用专用日志并保留诊断上下文。

对可被频繁触发的可靠 RPC，评估业务节流、请求合并和有界等待队列。节流不能让客户端永久等待，也不能用无回执丢弃替代正常失败处理。引用序号的生命周期、重连重置与整数回绕应有统一约定；不将长时间回绕风险当作当前已发生故障。

### 2.5 性能、配置和工程保障

- **必须**：先确定目标机器、客户端数量、服务器帧率目标和负载，再用相同场景比较优化前后 CPU、分配、网络流量与尾延迟。本文没有测得可用的固定预算，因此不编造“已达标”数值。
- **推荐**：局部交互使用附近候选集；装备同步按物品 ID 或已持有武器引用查找，避免每次扫全世界。
- **推荐**：UI 按变更范围刷新。已有版本门控应保留，是否需要条目级更新由实测决定。
- **推荐**：补给内容、数量、交互距离、搜索时长和槽位语义集中定义。项目已有 `UExtractionRules`（位于 `ExtractionAbilities.h`），应先复用现有配置体系。
- **按规模评估**：Fast Array、Iris、Replication Graph、GAS 和独立运行时模块。它们解决的对象不同，不构成搜打撤项目的必选套餐。
- **必须**：分清纯规则测试、组件测试、多人联网测试和打包验收。`git diff --check` 仅验证补丁格式，无法证明玩法、编译或网络正确。
- **推荐**：为库存、战斗、持久化设置独立日志类别；正常高频日志采用合适级别，错误日志携带请求号、容器 ID、版本及事务关联信息，不输出凭据。

### 3.2 P1：初始化忽略武器同步失败

**证据：** [ExtractionInventoryComponent.cpp](../../Source/BrokenEdge/Extraction/ExtractionInventoryComponent.cpp)，`InitializeLoadout` 37–86 行、`InitializeGuard` 113–127 行、`SyncWeapons` 169 行起。

初始化先设置 `bInitialized`、写入库存，随后直接调用 `SyncWeapons()`，没有检查返回值。而 `SyncWeapons` 在定义或武器类不可用、生成失败时会清理本次新建 Actor 并返回 `false`。对比之下，交互事务已检查该失败结果并恢复数据。

**判断：源码确认的失败传播缺口；运行后果属于条件性风险。** 缺少武器资源时可能留下已初始化的库存而没有对应武器表现，同一世界的初始化门控又阻止直接重试。尚未证明正常资源下会出现。

**建议：** 初始化按候选库存、装备准备、成功提交组织；失败显式进入可恢复状态，保留旧状态并向上层报告。成功标记应在必要步骤完成后设置。不能只把 `bInitialized` 移到末尾而忽略已生成的补给 Actor，否则重试可能重复发放。

**验收：** 注入主武器成功、副武器失败，以及首个武器失败；检查旧装备、候选装备清理、库存、初始化状态和再次重试，确认无重复物品及残留 Actor。

### 3.3 P1：开局溢出补给生成失败后没有保留或补偿

**证据：** 同一文件 `InitializeLoadout` 56–83 行。`GrantStartingSupply` 返回局部 `Overflow`；生成地面容器失败时仅输出 `EXTRACTION_STARTING_SUPPLY_SPAWN_FAILED`，随后继续初始化，没有保存该溢出容器用于重试。

**判断：源码确认；只在生成失败时触发。** 丢失的是本次应发放的溢出补给，不能扩大成“玩家原有装备必然丢失”。

**建议：** 将溢出部分纳入同一次发放状态，使用可重试的待发放记录或整体回滚，确保重试不会重复已经放入背包或已落地的补给。

**验收：** 满背包、只剩部分堆叠空间、副槽占用三种情况下强制容器生成失败，再恢复生成；最终补给总数与规则一致。现有 [ExtractionStartingSupplyTests.cpp](../../Source/BrokenEdge/Tests/ExtractionStartingSupplyTests.cpp) 检查容量、溢出及持久化，但该文件没有执行世界容器生成失败路径。

### 3.4 P1 核查项：整体掉落失败不能通过返回值通知上层

**证据：** [ExtractionInventoryComponent.cpp](../../Source/BrokenEdge/Extraction/ExtractionInventoryComponent.cpp)，`DropAll` 299–322 行；[ExtractionInteractionComponent.cpp](../../Source/BrokenEdge/Extraction/ExtractionInteractionComponent.cpp)，`DropOnExit` 460 行起。

`DropAll` 创建失败会保留库存，这是正确的局部保护；但函数返回 `void`，`DropOnExit` 也没有结果传播。上层无法通过调用结果判断是否可以继续结束角色生命周期。

**判断：接口限制已确认；最终是否丢失仍需沿具体死亡、离局、断线和恢复路径验证。** 本文不把持久化恢复已经覆盖的情况重复列为确定损失。

**建议：** 返回明确结果，由退出流程决定重试、保存待掉落状态或补偿；列清“已结算但尚未成功生成世界掉落物”的恢复语义。不能仅靠错误日志作为恢复方案。

**验收：** 强制生成失败后分别触发死亡、主动退出、断线和世界销毁；检查角色清理、剩余内存资产和恢复后的来源批次总量。

### 3.5 P2：公开库存和分散的修改协议

**证据：** [ExtractionInventoryComponent.h](../../Source/BrokenEdge/Extraction/ExtractionInventoryComponent.h)，23 行的 `Contents` 为公开可写成员；实现中的 `Changed` 158 行不增加版本，`RecordShot` 260 行自行增加版本并请求网络更新；交互 `Execute` 直接修改和恢复库存。

**判断：源码确认的封装问题，不等于已发现漏增版本。** 调用方必须记住版本推进、武器同步、备弹刷新、复制通知和失败回滚的组合规则。新增物品操作时容易漏掉其中一项。

**建议：** 逐步提供只读视图和受控事务入口，集中提交变化与通知；明确一笔事务推进哪一层版本。不要机械地给 `Changed()` 增加 `++Revision`，现有调用可能已经增加版本。

**验收：** 为移动、拆分、堆叠、附件、装填、射击、结算建立变更矩阵，确认实际修改有通知、无效操作不意外提交，失败不遗留半完成状态。

### 3.6 P2：库存组件承担过多装备表现职责

**证据：** 同一实现 `SyncWeapons` 169–234 行直接操作战斗组件的主副武器、挂点、弹药回执、第一人称武器刷新及角色转向；`SyncReserve` 142–152 行直接写 `CarriedAmmo` 与固定突击步枪键。

**判断：源码确认的耦合。** 当前兼容已有战斗系统可以工作，但扩展武器类型、手持状态或新角色会同时影响库存、角色和旧战斗组件。

**建议：** 先建立装备同步适配边界，保留现有主副槽行为，通过明确结果表达准备失败；备弹查询按当前武器弹种与类型映射。不要立刻为此引入 GAS 或重写全部战斗逻辑。

**验收：** 玩家和守卫装备、切枪、卸枪、不同弹种装填、第一/第三人称切换，验证武器实例 ID、弹匣、备弹和挂点一致。

### 3.7 P2：全世界遍历形成扩展成本

**证据：** 库存 `SyncWeapons` 每个武器槽执行 `TActorIterator<AWeapon>`；交互 `UpdateFocus` 84 行起遍历战利品和钥匙门；组件 Tick 间隔为 0.1 秒，只有本地控制角色调用焦点更新。`DropPosition` 315 行起和开局补给放置还会遍历多个 Actor 类型构建忽略列表。

**判断：遍历事实确认，性能影响待测。** 不应误写为“每个客户端每帧扫描所有角色”，也不能据此断言当前地图已经卡顿。

**建议：** 测量后优先使用附近交互候选、已有装备引用或受控注册表；处理销毁、切图、Streaming 加卸载和引用失效。为碰撞忽略规则检查专用碰撞配置的适用性。

**验收：** 固定玩家位置，逐步增加战利品、门和武器数量，对比焦点选择正确性与耗时；覆盖候选 Actor 被销毁和卸载。

### 3.8 P2：库存版本、复制和 UI 更新粒度偏粗

**证据：** `RecordShot` 每次记录射击都会增加库存版本并 `ForceNetUpdate`；[ExtractionItems.h](../../Source/BrokenEdge/Extraction/ExtractionItems.h) 284 行起容器包含普通物品数组；[LootingMainView.cpp](../../Source/BrokenEdge/Extraction/LootingMainView.cpp) 的 `Refresh` 347 行起在版本变化时重建对应装备和容器。

**判断：更新机制确认，网络成本和 UI 耗时待测。** 不能从普通复制属性断言“每发子弹完整发送整个背包”。UI 已有打开状态和版本门控，且射击入口检查背包打开状态，因此也不能宣称玩家正常开背包时持续射击导致每发重建。

**建议：** 测量射击、搜索揭示和连续整理背包三类负载；必要时区分结构变化与数量/弹药变化，使用条目更新或增量复制。复制方案变更不得绕过来源批次保护和可见性规则。

**验收：** 记录网络字节、复制属性成本、UI 构建耗时和分配；优化后检查过期版本拒绝与界面最终收敛。

### 3.9 P2：持久化同步全快照写入的增长成本

**证据：** [ExtractionPersistence.cpp](../../Source/BrokenEdge/Extraction/ExtractionPersistence.cpp)，`Commit` 318–353 行将候选状态转为 JSON，追加文件并调用 `Flush(true)`，成功后更新内存状态；`SettlePlayer` 同步调用持久化结算。

**判断：同步序列化与 I/O 确认，卡顿及容量瓶颈待测。** 当前已经有日志校验、失败锁定及恢复测试，不属于“完全没有事务”。

**建议：** 测量档案数量、历史记录增长下的序列化、刷盘和恢复耗时。确有压力再设计单写者队列、快照压缩或存储服务；异步化必须维持提交顺序、成功回执边界和崩溃恢复，不可只把函数扔到后台线程。

**验收：** 人工慢盘、写入失败、尾记录截断、重启恢复以及提交后回执前终止；全程检查资产与操作幂等。多服务器共享账号写入属于未来产品化设计，本轮未评估其可用性。

### 3.10 P2：错误与 RPC 入口还缺少统一业务约定

**证据：** [ExtractionPlayerController.cpp](../../Source/BrokenEdge/Extraction/ExtractionPlayerController.cpp)，`ServerItemOperation_Implementation` 234 行起直接执行并回传 `FString`；`ClientItemResult_Implementation` 248 行起显示文本。交互 `Execute` 使用中文字符串表示拒绝，库存和事务日志使用 `LogTemp`。

**判断：文本耦合、日志分类现状确认。** 在检查的物品操作入口未见业务级速率限制，但这不是“引擎没有网络限制”或“已证明可利用攻击”。

**建议：** 统一错误码、显示文本和日志映射；为请求建立有界频率策略并明确被限流回执。继续保留现有序号、版本和权限校验。

**验收：** 高频有效/无效请求、连续过期请求以及结果与属性先后到达；客户端能结束等待，服务器不重复执行，日志可关联同一请求。

### 3.11 P2/P3：配置、资源入口和可读性需要收敛

**证据：** 库存 `GrantStartingSupply` 90–109 行硬编码 `SCARH`、`Ammo76251`、60 发和副槽 1，逐发尝试放入；[ExtractionItems.cpp](../../Source/BrokenEdge/Extraction/ExtractionItems.cpp) 的 `Ids` / `Get` 33–62 行维护白名单并通过固定路径 `LoadObject`；库存头文件与实现重复了多段相同注释。`Reload`、`CaptureWeapons` 等使用单字母变量和无括号嵌套控制流。

**判断：源码确认。** 白名单有安全和内容控制价值，不应移除成客户端任意资源路径；`LoadObject` 调用也不意味着每次都重新从磁盘加载。逐发放置保证零散堆叠可补齐，不能直接换为一次放置而改变结果。

**建议：** 补给规则数据化，槽位使用有名字的语义，定义注册与 Cook 验证统一；加载策略根据首次加载测试调整。重命名和格式整理分批进行，头文件保留契约、实现保留算法原因。

**验收：** 不改 C++ 即可调整补给；未知定义失败可解释；打包环境定义可加载；原有部分堆叠和溢出用例保持一致。

## 4. 验证计划：已有测试与应补证据

已有测试不是空白：[ExtractionInventoryTests.cpp](../../Source/BrokenEdge/Tests/ExtractionInventoryTests.cpp) 包含 `GridTransactions`、`StackConservation`、`EquipmentAndValidation`、`GearContainers`；[ExtractionPersistenceTests.cpp](../../Source/BrokenEdge/Tests/ExtractionPersistenceTests.cpp) 包含事务、来源恢复、`JournalFailures` 和崩溃边界；[ExtractionDriverTests.cpp](../../Source/BrokenEdge/Tests/ExtractionDriverTests.cpp) 有进程驱动及重复请求能力。下面列的是应验收的场景，不等于仓库里全部没有相关测试。

| 场景 | 层级 | 应证明什么 |
|---|---|---|
| 移动、旋转、拆分、合并、满包 | 规则测试 | 数量、来源守恒，失败保留原状态 |
| 两人取同一物品 | 两客户端＋服务器 | 只有一个有效提交，无重复资产，失败方刷新 |
| 重复、旧版本、旧会话、未搜索目标 | 请求与联机测试 | 拒绝原因明确，不改变权威资产 |
| 主/副武器或溢出容器生成失败 | 组件故障注入 | 无半初始化、无残留、可重试且不重复发放 |
| 死亡/退出掉落失败 | 生命周期集成测试 | 上层收到失败，资产有明确保留或补偿路径 |
| 射击、换弹、切枪与网络延迟 | 多人网络模拟 | 弹匣、备弹、来源及预测回执最终一致 |
| 搜索中目标被他人取走、距离变化 | 多人交互测试 | 旧请求失效、会话关闭或刷新、不泄漏未揭示数据 |
| 死亡、撤离、主动退出、断线相邻发生 | 结算集成测试 | 终态确定、结算至多一次、清理不重复掉落 |
| 慢盘、写失败、截断、提交后未回执即终止 | 持久化故障测试 | 仅承认已持久提交记录，恢复不增发或丢失已承诺资产 |
| 满物资地图、长时间会话和大档案 | 性能测试 | 同场景记录 CPU、带宽、UI 分配及恢复时间 |
| 切图、Pawn 替换、PIE 关闭 | 生命周期测试 | 无过期回调和失效引用，无重复补给或结算 |
| 独立服务器和客户端打包 | 发布验收 | 非编辑器环境可加载资源并完成出战—搜集—战斗—撤离闭环 |

测试运行记录应包含提交号、工作区差异、地图、进程角色、人数、网络模拟参数、日志/报告路径和最终结果。历史证据可作回归参照，不能替代当前代码的重新验收。

## 5. 分阶段整改建议

| 阶段 | 交付物与顺序 | 验收标准 |
|---|---|---|
| A：失败恢复 | 先为初始化、溢出补给和整体掉落增加故障注入；明确并实现失败传播、重试与补偿状态 | 第 3.2–3.4 节场景通过，无重复资产；完成对应多人/生命周期验证 |
| B：状态和接口 | 在 A 的测试保护下收敛库存写入口、装备适配、错误码、变更通知及日志；小批量迁移调用方 | 原有规则测试通过；所有写路径有明确版本/提交责任；正常玩法和兼容数据不变 |
| C：配置与可读性 | 数据化补给，集中槽位语义；整理高风险函数命名、括号及重复注释 | 配置变更可验证；格式与行为修改分开；必要的反射迁移已验证 |
| D：测量后优化 | 建立固定负载基线，按结果优化候选查询、装备查找、复制/UI 与持久化 | 同机同负载有可复核前后数据；性能改动未破坏一致性测试 |

阶段 A 的自动化场景与 B 的职责收敛优先于全项目格式化。暂不整体改写为 GAS，不强制迁移复制系统，不一次性拆分所有模块，不扩展成商业后端或反作弊平台开发。
